# Ticket Stream v1 - k6 부하 테스트 가이드

이 문서는 **k6**를 활용하여 Ticket Stream v1의 **동시성 락 전략(비관적 락, 낙관적 락, 락 미적용)**의 데이터 정합성과 트래픽 폭주 한계를 검증하는 실행 가이드입니다.

---

## 1. 사전 준비 (Pre-requisites)

부하 테스트를 실행하기 전, 백엔드와 DB가 정상 구동 중이어야 합니다.

```powershell
# 1. PostgreSQL DB 컨테이너 실행 (Docker Compose)
docker-compose up -d

# 2. 백엔드 Spring Boot 실행 (새 터미널 또는 IDE)
.\gradlew.bat bootRun

# 3. k6 설치 확인 (v2.4.0 이상)
k6 version
```

---

## 2. 부하 테스트 시나리오 요약

| 시나리오 | 동시 요청 (VUs) | 대상 락 전략 | 핵심 검증 목표 | 기대 결과 |
| :--- | :---: | :---: | :--- | :--- |
| **1. 비관적 락 정합성 검증** | **15 ~ 30명** | `PESSIMISTIC` | 단일 좌석 동시 선점 시 1건만 성공하고 더블 부킹이 없는지 확인 | • 200 OK: **1건**<br/>• 400 Bad Request: **`VUs - 1`건**<br/>• 500 에러: **0건** |
| **2. 낙관적 락 충돌 검증** | **15명** | `OPTIMISTIC` | 커밋 시점 @Version 비교로 1건만 성공하고 후행자는 롤백되는지 확인 | • 200 OK: **1건**<br/>• 409 Conflict: **`VUs - 1`건**<br/>• 500 에러: **0건** |
| **3. 비관적 락 트래픽 폭주** | **100 ~ 150명** | `PESSIMISTIC` | 락 대기 지연으로 인한 커넥션 풀 고갈 및 3초 타임아웃 한계 체감 | • 200 OK: **1건**<br/>• 400 Bad Request: **약 80건**<br/>• 500 에러: **약 40건 (타임아웃 폭발)**<br/>• 다른 API까지 마비되는 연쇄 장애 확인 |
| **4. 락 미적용 결함 재현** | **15명** | `NONE` | 락이 없을 때 동일 좌석에 중복 결제(더블 부킹)가 발생하는지 확인 | • 200 OK: **2건 이상 (더블 부킹 발생)**<br/>• 데이터 정합성 파괴 증명 |

---

## 3. k6 실행 방법

### 3.1 [시나리오 1] 비관적 락 기본 정합성 테스트 (15명 동시 요청)
단 1개의 좌석(ID: 1)에 15명이 동시에 예매를 시도합니다.

```powershell
k6 run k6/pessimistic-lock-test.js
```

#### CLI 옵션으로 가상 사용자(VUs) 수 즉석 변경:
```powershell
# 30명 동시 요청으로 실행
k6 run --vus 30 --iterations 30 k6/pessimistic-lock-test.js
```

---

### 3.2 [시나리오 2] 낙관적 락(@Version) 충돌 검증 테스트 (15명 동시 요청)
동시 요청 중 1등만 커밋 성공하고 나머지는 409 Conflict로 롤백되는지 확인합니다.

```powershell
k6 run k6/optimistic-lock-test.js
```

---

### 3.3 [시나리오 3] 비관적 락 트래픽 폭주 및 병목 한계 테스트 (120명 동시 요청)
HikariCP 커넥션 풀(10개)과 3초 타임아웃의 한계를 초과시켜 **대량의 500 타임아웃 에러와 시스템 지연을 체감**하는 테스트입니다.

```powershell
k6 run k6/pessimistic-overload-test.js
```

> **🔥 폭주 체감 팁**:  
> k6가 도는 3~5초 동안 브라우저에서 메인 화면(`http://localhost:3000`)을 새로고침해 보세요.  
> 1개 좌석의 락 경합 때문에 커넥션 풀이 말라붙어 **공연 목록 조회(`GET /concerts`)조차 3초간 멈추는 연쇄 장애**를 직접 확인할 수 있습니다.

---

### 3.4 [시나리오 4] 락 미적용(NONE) 더블 부킹 결함 재현 테스트
락이 없을 때 레이스 컨디션으로 인해 동일 좌석에 중복 예매가 발생하는 결함을 재현합니다.

```powershell
k6 run k6/no-lock-test.js
```

---

### 3.5 실시간 웹 대시보드로 시각화하여 실행하기 (강력 추천!)
k6 내장 웹 대시보드를 띄워 웹 브라우저에서 초당 요청 수(RPS)와 응답 지연 시간 그래프를 실시간으로 확인합니다.

> **⚠️ 주의 (`http://127.0.0.1:5665` 접속 불가 현상 원인 및 해결)**:  
> 대시보드 포트(`5665`)는 **"k6 명령어가 터미널에서 실행 중인 동안에만" 열리는 실시간 임시 웹 서버**입니다.  
> 단발성 테스트(1회 반복)는 **단 0.7초 만에 끝나고 프로세스가 즉시 종료**되므로, 테스트 종료 후 브라우저로 접속하면 이미 꺼져 있어 접속되지 않습니다.  
> 따라서 아래 3가지 방식 중 하나로 실행하세요:

#### 방법 A: 실행 즉시 브라우저 자동 오픈 (`open=true`)
명령어 실행과 동시에 기본 웹 브라우저에 대시보드 탭이 자동으로 열립니다.
```powershell
k6 run --out web-dashboard=open=true k6/dashboard-test.js
```

#### 방법 B: 20초간 지속되는 대시보드 전용 테스트 실행
대시보드 그래프를 여유롭게 관찰할 수 있도록 20초 동안 지속 부하를 발생시키는 스크립트를 실행합니다.
```powershell
k6 run --out web-dashboard k6/dashboard-test.js
```
실행 중인 20초 동안 브라우저에서 `http://127.0.0.1:5665`로 접속하여 실시간 차트를 확인합니다.

#### 방법 C: 테스트 종료 후에도 언제든 볼 수 있는 HTML 리포트 저장 (`export`)
테스트가 끝난 후에도 차트와 수치를 영구적으로 열어볼 수 있도록 단일 HTML 리포트 파일로 내보냅니다.
```powershell
k6 run --out web-dashboard=export=report.html k6/pessimistic-lock-test.js
```
테스트 완료 후 생성된 `report.html` 파일을 더블 클릭하면 브라우저에서 언제든지 인터랙티브한 대시보드를 확인할 수 있습니다.

## 4. k6 결과 리포트 지표 해석 가이드

테스트 완료 후 터미널에 출력되는 핵심 메트릭의 의미는 다음과 같습니다:

```text
    ✓ setup: seats reset successfully
    ✓ status is 200 (Winner) or 400 (Blocked)
    ✓ seat status is SOLD

    █ THRESHOLDS
    ✓ orders_success..........: count=1       <-- [핵심] 성공 건수가 단 1건이어야 정합성 100%
    ✓ orders_blocked_400......: count=14      <-- 정상 차단 건수 (소규모 시 VUs-1)
    ✓ orders_error_other......: count=0       <-- 타임아웃/500 에러 건수 (폭주 시 증가)

    █ HTTP METRICS
    http_req_duration..............: avg=35ms min=12ms med=28ms max=120ms p(95)=95ms
```

1. **`orders_success`**:  
   - 반드시 **정확히 `count=1`**이어야 합니다. 2 이상이면 데이터 정합성 실패(더블 부킹)입니다.
2. **`orders_blocked_400`**:  
   - 1등에게 밀려 정상적으로 "이미 판매된 좌석입니다" 비즈니스 예외를 받고 거절된 건수입니다.
3. **`orders_error_other` (500 에러 / 타임아웃)**:  
   - **0건인 경우**: 시스템이 정상 처리 가능한 트래픽 범위 내임.
   - **수십 건 이상 발생한 경우**: 현재 시스템(커넥션 풀 10개, 타임아웃 3초)의 수용 한계를 초과하여 락 대기 타임아웃이 폭발한 상태임.
4. **`http_req_duration (max, p95)`**:  
   - 줄의 맨 뒤에 선 사용자가 응답을 받기까지 기다린 시간입니다. VUs가 늘어날수록 선형적으로 증가합니다.
